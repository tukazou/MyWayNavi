## 1. システム概要

### アーキテクチャ

```
ブラウザ（フロントエンド）
　├── 地図表示画面
　├── ルート選択画面
　└── チャットパネル（地図右半分に重畳表示）
　↓ HTTP
バックエンド（Python + FastAPI / Cloud Run）
　├── /chat          ← Gemini API呼び出し
　├── /route         ← Google Maps API呼び出し
　└── /history       ← 走行履歴の読み書き
　↓
外部API
　├── Gemini API（Agent Platform / Vertex AI）
　└── Google Maps API
　↓
ローカルストレージ
　└── 走行履歴JSON（ユーザー端末に保存）
```

### 技術スタック

| レイヤー | 技術 |
|---|---|
| フロントエンド | HTML / CSS / JavaScript |
| バックエンド | Python 3.11 + FastAPI |
| AI | Gemini API（Agent Platform） |
| 地図・ルート | Google Maps API |
| デプロイ | Cloud Run |
| CI/CD | GitHub Actions → Cloud Run |
| データ保存 | ローカルJSON（プライバシー保護のためサーバー非保存） |

## 2. 画面設計

### 画面一覧

| 画面 | 説明 |
|---|---|
| 地図表示画面 | 現在位置を表示するメイン画面 |
| ルート選択画面 | 目的地までの全体図とルート比較を表示 |
| チャットパネル | 地図右半分に重畳表示。音声実装後は不要 |

### 画面詳細

**① 地図表示画面**
- 現在位置をリアルタイム表示
- 走行中のルートをオーバーレイ表示
- チャットパネルの表示/非表示切り替え

**② ルート選択画面**
- 目的地までの全体図を表示
- 複数ルート候補を色分けで表示
- 各ルートの所要時間・距離・高速料金を比較表示
- ユーザーがルートを選択するとナビ開始

**③ チャットパネル（暫定UI）**
- 地図右半分に重畳表示
- テキスト入力 → Geminiの返答を表示
- 将来的に音声入出力（STT/TTS）に置き換え予定

## 3. APIエンドポイント設計

### 3.1 `/chat` - 会話エンドポイント

**メソッド**：POST

**リクエスト**：
```json
{
  "message": "今日は、Movix柏の葉までのルートを出して",
  "context": {
    "current_location": {
      "lat": 35.6481,
      "lng": 140.0468
    },
    "user_profile": {
      "vehicle_width": 1840,
      "preferred_roads": ["広い道", "慣れた道"]
    }
  },
  "conversation_history": []
}
```

**レスポンス**：
```json
{
  "reply": "映画館ですね。作品の上映時刻は何時ですか？",
  "action": null
}
```

**actionの種類**：
- `null`：返答のみ
- `"show_routes"`：ルート選択画面を表示
- `"start_navigation"`：ナビ開始
- `"show_detour"`：迂回案を表示

## 4. Geminiエージェント設計

### 4.1 システムプロンプトの方針

```
あなたはMyWayNaviというAIドライビングパートナーです。
ドライバーの好み・走行履歴・車種を理解し、先回りして行動します。

【基本姿勢】
- 押しつけない。最終判断は必ずドライバーに委ねる
- 簡潔に話す。運転中なので長い説明は避ける
- 状況を解釈して伝える（情報の羅列ではなく）

【ドライバーの情報】
- 車種：{vehicle_type}（全幅：{vehicle_width}mm）
- 好みのルート傾向：{route_preferences}
- 直近の走行履歴：{recent_trips}

【現在の状況】
- 現在地：{current_location}
- 目的地：{destination}
- 時刻：{current_time}
```

### 4.2 主要な会話フロー

**目的地入力時**
1. 目的地の性質を判断（映画館→時刻制約あり、公園→下道優先）
2. 走行履歴から好みのルートを参照
3. 複数案を比較してユーザーに提示

**渋滞検知時**
1. 渋滞の規模・予測を取得
2. 迂回案を計算
3. 「並ぶ/迂回」の選択肢を状況説明付きで提示

**目的地近接時**
1. 駐車場・入口情報を提示
2. 目的に応じた入口を案内（例：映画館に近い駐車場棟）

## 5. データ設計

### 5.1 走行履歴の保存方針

- **保存場所**：ユーザーのローカル端末（プライバシー保護）
- **形式**：JSON
- **保存パス**：`~/.mywaynavi/history/`
- **サーバーへの送信**：なし

### 5.2 ユーザープロファイル

```json
{
  "vehicle": {
    "type": "Mazda CX-8",
    "width_mm": 1840
  },
  "preferences": {
    "avoid_narrow_roads": true,
    "preferred_road_types": ["wide", "familiar"],
    "congestion_tolerance": "low"
  },
  "learned_patterns": {
    "frequent_destinations": [],
    "preferred_highway_entries": [],
    "typical_departure_times": []
  }
}
```

## 8. 実装スコープ

### MVP（必ず作る）

- テキスト入力 → Gemini応答
- Google Maps APIでルート計算・比較
- 走行履歴のローカル保存・読み込み
- デモシナリオ（Movix柏の葉）の動作
- Cloud Runへのデプロイ
- GitHub Actions CI/CD

### Should（余裕があれば）

- 音声入力・出力（STT/TTS）
- 地図のリアルタイム表示
- 渋滞のリアルタイム検知

### Won't（今回はやらない）

- 走行履歴の自動学習ループ
- 駐車場のリアルタイムデータ連携
- トイレ休憩提案機能
- 同乗者プロファイル

## 9. 今後の課題

- **プロンプト肥大化**：走行履歴が増えるとトークン数が増加。将来的には走行履歴を「好みプロファイル」として圧縮して渡す設計が必要
- **プロンプト矛盾**：相反する走行パターンが蓄積された場合の優先順位設計
- **音声UI**：運転中のスマホ操作は法律上禁止。STT/TTSが本来の姿
- **オフライン対応**：トンネル内など通信が途切れた場合の挙動
